为什么要做这个

一是想提升一下自己的编程的综合能力. 写个代码大家都会, 毕竟就是一门语言, 还是语法十分简单的语言. 但是编程的尽头是项目设计

三是 Ren'Py 的文档真是烂到了一种程度. 这一点我觉得甚至能拉出好几个子条目来说.

一个会去看你文档的人真正想看的是什么? 首先, 他肯定是有高度自定义的需求. 那么他会想看你引擎的工作原理, 会想看你类里的继承组合关系, 会想看你引擎运行时各个组件的生命周期. 说白了, 一个会去翻你文档的人在某种程度上肯定希望能够以 纯 Python 的形式编写一个 Ren’py 游戏, 或者以 Python 包 的方式使用 Ren’py 引擎, 又或者是写一些 Ren’Py 插件供开源社区使用.类似下面代码的感觉:

1. Ren'py 引擎的文件结构

本文档最开始撰写时, Ren'Py 引擎是 Windows 系统上的 8.3.7 版本, 但在更新到 8.5.* 版本后, Ren’Py 将内置的某些 Cython 包直接内嵌到它的 Python 运行时里了, 因此和这些库有关的说明可能过时

打开 Ren'Py 的文件存放位置, 文件夹和文件清单如下:

文件夹

  • doc :保存 Ren'Py 说明文档的文件夹. 删除该文件夹不影响 Ren'Py 引擎运行.
  • gui :预定义了一些 GUI 模板 文件. 新建一个Ren'Py 项目时, 该文件夹的内容将被拷贝至项目文件夹.
  • launcher: 预定义的一个 Ren'Py 项目. 也是 Ren’Py 引擎的 UI. 你可以理解为你最熟悉的 Ren'Py 引擎的 UI 其实也是一个 Ren'Py 游戏, 如果你打开这个文件夹, 你会发现它的文件结构和一般的 Ren'Py 项目一致.
  • lib: Ren'Py 的运行时. 也就是 Ren'Py 使用的 Python 环境.
  • module: 编译 Ren'Py 使用的某些二进制 Python 依赖包使用的资源. 由于 Ren’Py 引擎已经编译完成, 删除该文件夹不影响 Ren'Py 引擎运行.
  • renpy: Ren'Py 引擎的本体. 这个文件夹的内容将是后续讨论的重点 (也几乎是全部) 内容
  • renpy.app: MacOS 上 Ren'Py 的软件. 相当于 Windows 下的 renpy.exe
  • sdk-fonts: Ren'Py 自带的默认字体.
  • the_question: 预定义的一个 Ren'Py 项目. 你在 Ren'Py 引擎界面看到的同捆的那个示例项目
  • tmp: Ren'Py 引擎的调试信息的输出位置. 准确的说, 是上面说到的 launcher 这个项目调试信息的输出位置
  • tutorial: 和上面说到的 the_question 相同,预定义的一个 Ren'Py 项目. 你在 Ren'Py 引擎界面看到的同捆的那个示例项目
  • update: Ren'Py 引擎的更新日志保存位置

文件

LICENSE, LICENSE.txt: Ren'Py 的版权信息, 删除该文件不会影响 Ren'Py 引擎的运行, 但这很没素质了

renpy.exe : Windows 下的可执行文件

renpy.sh : Liunx 下的执行脚本

renpy.py : Ren'Py 的程序入口

在下一节, 我们将讨论 Ren'Py 是怎么运行起来的, 这些内容从 renpy.sh 可一窥究竟.

手动编译 pygame_sdl2?

如果你有能力自己手动编译适用你的 Python 版本的 pygame_sdl2, 那么该文档显然不适合你了, 你完全有能力自己阅读 Ren'Py 的源码, 而不是该文档.

事实上, 我自己尝试编译适用于我自己使用的 Python 3.13 版本的 pygame_sdl2 还没有成功, Cmake显然不是一个 Python + .NET 爱好者擅长的领域, 我的评价是不如 nuget 一根

当然你也有一个取巧的办法, 就是把 Ren'Py 自带的 pygame_sdl2 包抠出来塞到你的 python 环境中. 当然, 前提是你的 Python 环境也是 3.9 的话 (理论上可行, 但我自己没有尝试过. 话说 Python 3.9 已经是 EOL 了, Ren'Py 却刚把它作为运行时. 唉, 遗老)

现在(2026年7月23日)的最新版本是 Ren'Py 8.5.2 , Python 解释器已经是 3.12 了.

那么, Ren'Py 是怎么成功运行这个脚本的呢? 它所依赖的 pygame_sdl2 在哪里呢? 打开 renpy 文件夹, 我们并没有发现 pygame_sdl2 这个子包. 也就是说, pygame_sdl2 这个包直接存在于 Ren'Py 的 Python 环境中, 而不是存在于 renpy 引擎自己的包中.

上面这段话有点绕, 你可以这样理解: pygame_sdl2 这个包存在于 Ren'Py 使用的 python 环境中, 就类似于 os, typing, 等这些原生包中, 而不是像你在工作文件夹中建立了一个文件夹, 其中存放了 __init__.py , 把这个文件夹告诉 python “我是一个包, 你可以 import 我”.

我们把目光转移到 renpy.sh 上. 前面说过, 该脚本文件相当于 Linux 系统上的 renpy.exe, 就是用来启动 Ren'Py 引擎的. 不同的是这是一个脚本文件, 类似于 Windows 上的 *.bat 文件. 回想一下, 你在玩 “学习版” 或者 mod版 的某些游戏时, 是不是会有一个类似于 “运行游戏点击这个” 的 *.bat 文件? 与之类似, 这类脚本文件通常是设置了一些系统变量, 之后再启动对应的可执行文件, 以实现某些设置(比如加载汉化文件, 为了运行老游戏的兼容性优化, 设置分辨率等操作.)

总之, 虽然我们无法一窥 renpy.exe 内部的运行, 但同样功能的 renpy.sh 却是可以直接打开的.总而言之, 我们打开该文件, 大致了解一下其中的操作.

#!/bin/sh
# 声明这是一个 shell 脚本，使用 /bin/sh 解释器执行

PYTHON="py3"
# 设置 Python 解释器的名称为 "py3"

SCRIPT="$0"
# $0 代表当前脚本的名称，将其保存在 SCRIPT 变量中

# Resolve the chain of symlinks leading to this script.
# 解析指向当前脚本的所有符号链接，找到真实路径
while [ -L "$SCRIPT" ] ; do
    # -L 测试文件是否为符号链接，当 SCRIPT 是符号链接时循环继续
    LINK=$(readlink "$SCRIPT")
    # readlink 命令读取符号链接的目标，即 SCRIPT 指向的文件

    case "$LINK" in
        /*)
            # 如果链接以 / 开头(绝对路径)，则直接使用
            SCRIPT="$LINK"
            ;;
        *)
            # 否则(相对路径)，将其与当前目录结合
            SCRIPT="$(dirname "$SCRIPT")/$LINK"
            # dirname 获取 SCRIPT 所在的目录，然后与 LINK 拼接
            ;;
    esac
    # case 语句结束
done
# 循环结束后，SCRIPT 变量包含真实文件路径，不再是符号链接

# The directory containing this shell script - an absolute path.
# 获取包含此脚本的目录的绝对路径
ROOT=$(dirname "$SCRIPT")
# 提取 SCRIPT 的目录部分
ROOT=$(cd "$ROOT"; pwd)
# 进入该目录并执行 pwd，获取绝对路径

# The name of this shell script without the .sh on the end.
# 获取脚本名称，去掉 .sh 后缀
BASEFILE=$(basename "$SCRIPT" .sh)
# basename 命令提取文件名，第二个参数指定要去掉的后缀

if [ -z "$RENPY_PLATFORM" ] ; then
    # -z 测试字符串是否为空，如果环境变量 RENPY_PLATFORM 未设置则执行下面的代码
    RENPY_PLATFORM="$(uname -s)-$(uname -m)"
    # 使用系统名称(uname -s)和机器硬件名称(uname -m)组合设置平台标识

    case "$RENPY_PLATFORM" in
        # 根据检测到的平台标识进行具体分类
        Darwin-*|mac-*)
            # 匹配 macOS (Darwin 是 macOS 的内核名)
            RENPY_PLATFORM="mac-universal"
            ;;
        *-x86_64|amd64)
            # 匹配 64 位 x86 架构
            RENPY_PLATFORM="linux-x86_64"
            ;;
        *-i*86)
            # 匹配 32 位 x86 架构(如 i386, i586, i686 等)
            RENPY_PLATFORM="linux-i686"
            ;;
        Linux-*)
            # 匹配其他 Linux 平台，保留检测到的具体架构
            RENPY_PLATFORM="linux-$(uname -m)"
            ;;
        *)
            # 默认情况下不做任何修改
            ;;
    esac
    # case 语句结束
fi
# if 语句结束

# 设置库文件路径，结合根目录、Python 版本和平台信息
LIB="$ROOT/lib/$PYTHON-$RENPY_PLATFORM"

if ! test -d "$LIB"; then
    # 检查 LIB 目录是否存在，如果不存在则执行下面的代码
    # 输出错误信息，提示用户平台文件未找到
    echo "Ren'Py platform files not found in:"
    echo
    echo "$LIB"
    echo
    echo "Please compile the platform files using the instructions in README.md"
    echo "or point them to an existing installation using ./after_checkout.sh <path>."
    echo
    echo "Alternatively, please set RENPY_PLATFORM to a different platform."
    exit 1
    # 退出脚本，返回错误代码 1
fi

if [ -e "$LIB/$BASEFILE" ] ; then
    # -e 测试文件是否存在
    # 如果以脚本名命名的可执行文件存在，则执行它
    exec $RENPY_GDB "$LIB/$BASEFILE" "$@"
    # exec 会替换当前进程，$RENPY_GDB 是可能设置的调试器
    # "$@" 传递所有命令行参数
fi

if [ -e "$LIB/renpy" ] ; then
    # 如果名为 renpy 的可执行文件存在，则执行它
    exec $RENPY_GDB "$LIB/renpy" "$@"
fi

# 如果以上文件都不存在，输出错误信息
echo "$LIB/$BASEFILE not found."
echo "This game may not support the $RENPY_PLATFORM platform."
exit 1
# 退出脚本，返回错误代码 1

renpy.sh 看起来主要做了以下工作:

  1. 初始化工作路径, 整个 while 块大致就是在做这些工作
  2. 选择 Python 环境. 包括 case 块的这部分的工作
  3. 启动 Python 环境. 我们注意到它启动了在 $LIB 占位符下的 renpy.

打开 lib 文件夹, 其中的文件结构一目了然: 三个平台对应的可执行 Python 环境 (理解为 Windows, MacOS, Linux 系统下的 python.exe 就行), 和一个 Python3.9 文件夹. 打开该文件夹不难看出, 这个文件夹存放着各种 Python 包, 我们心心念念的 pygame_sdl2 也赫然在列. 也就是说, 虽然 Python 可执行环境在三个平台上不同, 但是其包都是一样的, 没必要保存三份, 因此单独抽出来保存一份即可, 可供三个客户端同时使用.

现在我们知道了 Ren'Py 使用的 Python 环境和其包存放的位置, 理论上使用该环境执行 renpy.py 脚本, 就能实现和 renpy.exe 相同的效果. 让我们实践出真知:

1

你的 renpy.exe 文件夹路径> .\lib\py3-windows-x86_64\python.exe renpy.py

果然, 顺利的打开了 Ren'Py 引擎. 恭喜你, 你成功 以执行 Python 脚本的形式 运行了 Ren'Py 引擎. 现在对你而言, 你已经知道了 Ren'py 的程序入口点, 是时候从此入手, 了解 Ren'Py 的运行机制了.

renpy.exe, .\lib\py3-windows-x86_64\python.exe renpy.py, .\lib\py3-windows-x86_64\renpy.exe 的区别

你可能会发现, Ren'Py 的根目录下有一个 renpy.exe, .\lib\py3-windows-x86_64\ 目录下有 python.exe, pythonw.exe, renpy.exe. 这些个东西究竟有何不同? 我用命令行打开的界面和 renpy.exe 运行的引擎是同一个东西, 还是看上去一模一样的两个东西?

首先, renpy.exe 我个人觉得就是 Windows 版的 renpy.sh , 它设置了一些工作目录, 随后启动自带的 Python 环境, 并运行 renpy.py, 就这么简单. 至于 python.exe 和 pythonw.exe, 是你在运行 python 脚本的时候是否会弹出一个系统控制台, 就这么简单.

最后, 两个 renpy.exe有没有什么区别, 我觉得是没有的, 就只是一个拷贝, 仅此而已. 实际上, 你可以计算两个文件的哈希值并进行比较, 得到的结果是完全相同的, 这意味着两个 renpy.exe 完全相同

import hashlib
import os
import sys
from typing import Tuple, Optional


def calculate_file_hash(file_path: str, algorithm: str = 'sha256') -> str:
  """计算文件的哈希值"""
  hash_algo = hashlib.new(algorithm)

  with open(file_path, 'rb') as f:
      # 分块读取以处理大文件
      for chunk in iter(lambda: f.read(4096), b''):
          hash_algo.update(chunk)

  return hash_algo.hexdigest()


def find_first_difference(file1: str, file2: str) -> Optional[Tuple[int, bytes, bytes]]:
  """找出两个文件首次出现差异的位置"""
  with open(file1, 'rb') as f1, open(file2, 'rb') as f2:
      position = 0
      while True:
          chunk1 = f1.read(4096)
          chunk2 = f2.read(4096)

          # 文件读取结束
          if not chunk1 and not chunk2:
              return None

          # 长度不同
          if len(chunk1) != len(chunk2):
              min_len = min(len(chunk1), len(chunk2))
              # 先检查共同长度的部分
              for i in range(min_len):
                  if chunk1[i] != chunk2[i]:
                      return position + i, chunk1[i:i + 1], chunk2[i:i + 1]
              # 如果共同长度部分都相同，差异在于一个文件比另一个长
              return position + min_len, chunk1[min_len:min_len +
                                                1] if len(chunk1) > min_len else b'', chunk2[min_len:min_len + 1] if len(chunk2) > min_len else b''

          # 检查内容
          for i in range(len(chunk1)):
              if chunk1[i] != chunk2[i]:
                  return position + i, chunk1[i:i + 1], chunk2[i:i + 1]

          position += len(chunk1)


def compare_files(file1: str, file2: str) -> None:
  """比较两个二进制文件"""
  # 检查文件是否存在
  for file in [file1, file2]:
      if not os.path.exists(file):
          print(f"错误: 文件 '{file}' 不存在")
          return

  # 比较文件大小
  size1 = os.path.getsize(file1)
  size2 = os.path.getsize(file2)

  print(f"文件1: {file1} ({size1} 字节)")
  print(f"文件2: {file2} ({size2} 字节)")

  if size1 != size2:
      print(f"文件大小不同: {size1} vs {size2} 字节")

  # 计算和比较哈希值
  hash1 = calculate_file_hash(file1)
  hash2 = calculate_file_hash(file2)

  print(f"文件1 SHA256: {hash1}")
  print(f"文件2 SHA256: {hash2}")

  if hash1 == hash2:
      print("文件内容完全相同")
      return

  print("文件内容不同")

  # 查找第一个差异位置
  diff = find_first_difference(file1, file2)
  if diff:
      position, byte1, byte2 = diff
      print(f"首次差异位置: 字节 {position}")
      print(f"文件1内容: {byte1.hex()}")
      print(f"文件2内容: {byte2.hex()}")

3. 正式潜入 Ren'Py

3.1 Object: Ren’Py 的终极基类

在大致浏览 renpy 文件夹时, 很容易通过文件名称和文件夹名称猜测出各模块的作用. 其中, object.py 自然是我们首要关注的对象. 对于大部分 面向对象 的编程语言而言, object 类往往是所有类的基类, 定义了一些对于解释器/运行时而言十分重要的功能(比如实例的相等性比较和同一性比较)

然而, Ren’Py 的 Object 类并没有定义太多的方法和字段, 并且几乎只是重写了两个几乎很少用到的 dunder 方法: __setstate__ 和 __getstate__, 以及定义了一个类似于事件的函数列表 after_setstate

方法足够少, 适合作为一章的开始

__setstate__ 和 __getstate__ 主要用于类的序列化/反序列化. 在 Python 里, 序列化/反序列化不同于 .NET 的 Serialization, 通过 json 或者字典的格式保存/读取类的属性, 而是把类直接以二进制字节流的方式保存至磁盘/读取到内存. 大致可以想象为把类在内存里那一串 “0101” 直接复制出来写到一个文件里,读取时直接把它搬到内存里. 这个序列化过程一般通过 pickle 包实现, 文件后缀一般为 .pkl.

大名鼎鼎的 Python 数据处理的库 Pandas 的首选推荐方法即为 DataFrame.to_pickle()

.NET 和 pkl 对应的应该是 ‘bin’, 如果你在老软件的目录下见过以 .bin 结尾的文件, 那很有可能是序列化的 .NET 对象, 但和 *.bin 相关的方法已经过时了, .NET 并不推荐使用 (使用 NewtonSoft.Json 或者 System.Text.Json 是推荐的替代方案)

了解了什么是序列化/反序列化后, 再来看 Object 类的作用: 它修改了默认的序列化机制, 通过定义类的 nosave 字段, 把不需要序列化的属性/字段名添加到 nosave 里, 序列化时 Python就会忽略它们. after_setstate内的所有函数在 反序列化过程 __setstate__ 方法最后会被调用, 可以向里面注册任何需要的函数. 比如简单注册一个打印到控制台函数:

1

after_setstate = [lambda x: print("Object 已被反序列化")]

3.2 Sentinel: 属于 Ren’Py 的单例模式

在 object.py 文件下面, 还有一个名为 Sentinel 的类, 这个类简直是 Python 单例模式的教科书: 它重写了 __new__ 方法, 使得在程序运行期间, 有且仅有一个名为 name 的 Sentinel 对象.

Python 的 实例化 和 初始化

众所周知, 面向对象 的编程语言在创建一个对象的实例时, 一般会分为两个步骤:

  1. 为要创建的对象分配内存. 在可用的内存位置中标记指定长度的内存, 把占据这块内存的数据认为是对象的数据. 这个阶段是 实例化, 也就是 Python 中的 __new__ 方法. 也就是说, 在调用 __new__ 之后, Python 就认为创建的对象已经存在了, 因此 __new__ 方法才 需要 一个返回值, 返回的是实例化的对象 (在这个语境下, 用 “返回被标记为新建立的对象的内存位置”)
  2. 在 创建对象之后, 给对象的各个字段设置初始值, 这个阶段是 初始化, 也就是 Python 中的 __init__ 方法. 刚刚提到, 已经把某一块内存标记为对象的数据. 这段内存肯定不是从未使用过的, 它上面肯定有值(一串看起来毫无规律的0101), 如果不对对象进行初始化, 很难保证创建对象时的统一性. 这些残留的值会以难以预见的奇怪方式解释为当前占用这段内存对象的状态. 因此, 需要为对象设置 初始状态, 这就是初始化. 因此 __init__ 方法才 不需要 返回值, 因为 __init__ 只是在操作一个已经存在的对象.

从这个角度出发, 不难理解为什么 Python 的实例方法需要首先传入一个 self了, 这对于 Python 解释器来说, 指明了是在操作哪个对象. 相应地, __new__ 传入的是一个 cls, 对于 Python 解释器来说, 指明了是要创建哪个类的实例

Sentinel 的单例模式借助一个字典 sentinels 实现, 其中 key 为 Sentinel 对象的 name 属性, 值为 该 Sentinel 对象. 在有实例化需求时, Ren’Py 会先检查 sentinels 中是否有 key 为指定 “name” 的 Sentinel 对象, 如果有的话直接返回该对象, 不再创建新对象. 如果没有, 再进行对象的创建, 并添加到字典中.
